# DE program registry — design note

Status: proposal for review (Max). Nothing in this note is implemented.
Written 2026-09-10 after the Kindergeld ledger stack (#516–#542) and the
eligibility grid (#537, #538) merged.

## Problem

When rulespec-de lands a new module, nothing in this repo compares it. Each DE
output today is wired by hand in five places, and certification adds three
more. The wiring is spread across Python, YAML and JSON with no single place
that says "program X has outputs Y, checked by oracles Z, rooted at RuleSpec
nodes W". The same is true of every other jurisdiction, but DE is where the
encoder is about to deliver several modules at once (§§ 62–65 and § 32 EStG,
UhVorschG § 2 if it lands), so DE is where the cost lands first.

The Kindergeld leg producer is the sharpest instance: `scripts/de_executable.py`
hardcodes the program, the § 66 root node, the 13-household population and the
765 EUR household total (lines 76–82, 278–312, 489, 624, 895, 1092). A second
DE program cannot reuse it without editing constants.

## Where the wiring lives today

Per output (oracle comparison only):

| Step | File | What is written |
|---|---|---|
| Concept id | `axiom_oracles/core/case.py` | a `Concepts` constant |
| Oracle targets | `axiom_oracles/config/concept_mappings.yaml` | concept → EUROMOD and GETTSIM variable names, tolerance, category |
| Cases | `axiom_oracles/suites/de_*.py` + `axiom_oracles/suites/__init__.py` | a case list with per-engine projections, registered by name |
| Grid extract | `grids/de.yaml` | regenerated by `scripts/extract_grids.py --jurisdiction de` |
| Comparison | `comparisons/<suite>.yaml` | runner type, population, requested concepts |

Per output (Axiom leg):

| Step | File | What is written |
|---|---|---|
| Dependency plan | `comparisons/de-worker-dual-oracle/output-dependencies.json` | `view_id`, concept, oracle targets, `target_root_nodes`, `required_artifacts` (module path, signed manifest path, roles, nodes), `missing_dependency_roles` |
| Leg records | `scripts/de_axiom_legs.py` | reads the plan; emits `leg-pending` records until the module exists |

Per program (certification):

| Step | File | What is written |
|---|---|---|
| Program entry | `scripts/certify.py` `PROGRAMS["de/<program>"]` | period, suites with view ids, `computed_de_exercise` fields, closure artifact, executable status path |
| Spine scope | `scripts/de_closure_ledger.py` `_SPINE_SCOPES`, `_CAPTURED_MAX_DEPTH`, `_EXPECTED_SPINE_COUNTS` | corpus root and ordinal range or exact citations |
| Executable leg | `scripts/de_executable.py` | Kindergeld constants, replay, receipt, status |

Three DE programs exist in the ledger and certify tables (`de/kindergeld`,
`de/unterhaltsvorschuss`, `de/rv-employee-contribution`); only Kindergeld has
suites, a dependency plan and an executable leg.

## Proposal

One registry file per program under `conformance/de/programs/<program>.yaml`,
schema `axiom_oracles.de_program_registry.v1`, that is the single input the
scripts above read. Everything that is derivable is derived; only judgement
fields are hand-written.

```yaml
schema: axiom_oracles.de_program_registry.v1
program: de/kindergeld
period: "2025"
spine:                      # moves out of de_closure_ledger._SPINE_SCOPES
  kind: ordinal_range
  corpus_root: de/statute/estg
  first_ordinal: 62
  last_ordinal: 78
  captured_max_depth: 1
  expected_count: 18
outputs:
  - view_id: de/kindergeld
    concept: de:policies/worker_dual_oracle_baseline#kindergeld_monthly
    oracle_targets:           # today duplicated in concept_mappings.yaml
      euromod: bch00_s
      gettsim: kindergeld.betrag_m
    root_nodes:
      - de:statutes/estg/66#monthly_kindergeld_per_child
    suites:
      - suite: de-worker-dual-oracle
        population: de-worker-dual-oracle-13-households
        exercise_fields: [child_count, yearly_earned_income_total]
        golden_household_total: 765     # today a literal in de_executable.py
      - suite: de-kindergeld-eligibility
        population: synthetic   # 8 cases, no pinned population id yet
    dependency_roles:         # the human part of output-dependencies.json
      - role: monthly-amount
        node: de:statutes/estg/66#monthly_kindergeld_per_child
      - role: qualifying-child
        node: de:statutes/estg/32#qualifying_child      # not yet encoded
      - role: entitled-person
        node: de:statutes/estg/62#entitled_person       # not yet encoded
```

Derived from it, not written by hand:

- **Dependency plan.** `required_artifacts` comes from resolving each
  `dependency_roles[].node` against the pinned rulespec-de checkout: the
  module path is the node's citation path, and the signed manifest path is
  `.axiom/encoding-manifests/<module>.json`. A role whose node has no module
  on the pinned commit becomes `missing_dependency_roles`, and the leg stays
  `leg-pending`. This replaces the hand-maintained
  `output-dependencies.json`; the generated file is still committed so the
  hermetic checks keep a byte-stable input.
- **certify `PROGRAMS` entry.** Built from `program`, `period`, `outputs[].suites`
  and the closure artifact path convention already used for the pending
  programs.
- **Ledger spine tables.** `_SPINE_SCOPES`, `_CAPTURED_MAX_DEPTH` and
  `_EXPECTED_SPINE_COUNTS` read the `spine` block.
- **Concept mapping check.** `concept_mappings.yaml` stays the engine
  adapters' source of truth; a check asserts the registry's `oracle_targets`
  match it, so the two cannot drift.

Generalising the leg producer is the one real code change:
`scripts/de_executable.py` takes program, root node, population id and golden
total from the registry instead of module constants, and the 13-row
assertions become "one row per population case". The replay and receipt logic
does not change.

## What a new encoding then costs

1. A registry row per output (concept, oracle targets, root nodes, roles).
2. A suite that exercises it, if no existing grid does.
3. Run the generators; commit the derived plan and certificate.

No edits to `certify.py`, `de_closure_ledger.py` or `de_executable.py`.

## Non-goals

- Making other jurisdictions use it. The same shape would fit DK (one ledger,
  EUROMOD-only) and the US tariff lane, but that is a separate decision.
- Changing the CERTIFIED.md v3 semantics. The registry moves inputs, not
  verdict logic; the central gate and the ledger validators are untouched.
- Auto-discovering outputs from rulespec-de. Which outputs a program certifies
  is a judgement, so it stays hand-written.

## Open questions for Max

1. Should `dependency_roles` live here or in rulespec-de next to the module,
   as a declared "this module is complete for role R" statement? Here keeps
   the oracle repo self-contained; there lets the encoder assert closure at
   encode time. Recommendation: here, until the encoder emits such claims.
2. Does a GETTSIM-only output (Unterhaltsvorschuss, which EUROMOD DE_2025 does
   not simulate) get a registry row with one oracle target, or is single-oracle
   never a certified comparison? Recommendation: allow one target with a
   `single_oracle: true` flag that keeps `conformant` at attested, not
   computed.
3. Migrate Kindergeld first and keep the generated `output-dependencies.json`
   byte-identical as the acceptance test, or write UhV fresh as the first
   consumer? Recommendation: Kindergeld first; byte-identity proves the
   derivation before anything new depends on it.

## Sequencing

1. Registry schema + validator + Kindergeld registry file; derived plan
   byte-identical to the committed one. One PR, no behaviour change.
2. certify and ledger tables read the registry. One PR, certificates
   byte-identical.
3. Leg producer generalised; Kindergeld replay receipt unchanged. One PR.
4. First new consumer once the encoder run lands (§§ 62–65 roles flip from
   missing to present without any script edit).
